# PROMPT PARA CLAUDE — DASHBOARD DEL TÉCNICO DE CAMPO INSTALADOR DE INTERNET

Estoy desarrollando un sistema web para mi empresa ISP y necesito que continúes implementando el módulo correspondiente al **técnico de campo instalador de internet**.

## REGLA PRINCIPAL

**NO cambies el lenguaje de programación, framework, librerías, arquitectura ni estructura actual del proyecto.**

Debes continuar trabajando exactamente con:

* El mismo lenguaje de programación que ya estamos utilizando.
* El mismo framework.
* La misma estructura de carpetas.
* Los mismos modelos.
* El mismo sistema de autenticación.
* El mismo sistema de roles y permisos.
* El mismo frontend.
* Los mismos componentes.
* Los mismos estilos.
* Las mismas convenciones de código.
* La misma base de datos.

Antes de programar, revisa la estructura existente del proyecto y reutiliza todo lo que ya exista.

No quiero crear un proyecto nuevo.

No quiero cambiar de tecnología.

Quiero que esta funcionalidad quede integrada dentro del sistema que ya estamos desarrollando.

---

# OBJETIVO

Crear el **Dashboard Principal del Técnico de Campo Instalador de Internet**.

El técnico utilizará principalmente el sistema desde un teléfono celular, por lo que debe ser:

* Responsive.
* Compatible con PWA si actualmente el proyecto utiliza PWA.
* Rápido.
* Visualmente limpio.
* Fácil de utilizar en campo.
* Con botones grandes.
* Con información priorizada.

El técnico debe poder saber rápidamente:

1. Qué está pasando actualmente en la red.
2. Si existen torres, enlaces, OLT u otros equipos caídos.
3. Qué ocurrió durante la madrugada o desde su último ingreso.
4. Qué órdenes de trabajo tiene asignadas.
5. Cuál es su siguiente instalación.
6. Dónde se encuentra el cliente.
7. Qué trabajos ya realizó.
8. Qué incidencias pueden afectar a sus clientes.

---

# 1. ESTADO DE LA RED

En la parte superior del Dashboard mostrar una sección:

## ESTADO DE LA RED

Debe mostrar tarjetas/resumen:

🟢 Equipos en línea
🟡 Equipos con alerta
🔴 Equipos caídos

Ejemplo:

42 En línea
2 En alerta
1 Caído

La información debe provenir del módulo de monitoreo que ya exista en el sistema o de la estructura de monitoreo que actualmente estamos utilizando.

---

# MUY IMPORTANTE: SOLO LECTURA

El técnico **NO DEBE ADMINISTRAR LOS EQUIPOS DE RED**.

El técnico únicamente podrá consultar información.

No debe poder:

* Reiniciar equipos.
* Apagar equipos.
* Configurar equipos.
* Cambiar IP.
* Modificar parámetros.
* Ejecutar comandos.
* Eliminar equipos.
* Cambiar configuraciones.
* Entrar a credenciales.
* Visualizar contraseñas.
* Acceder a funciones administrativas.

El módulo de monitoreo para el técnico debe ser **100 % SOLO LECTURA**.

Aplicar permisos tanto en frontend como principalmente en backend.

Nunca confiar únicamente en ocultar botones desde la interfaz.

---

# 2. INCIDENCIAS ACTIVAS

Debajo del estado general mostrar:

## INCIDENCIAS ACTIVAS

Si existe una torre, OLT, radioenlace, router principal, switch u otro equipo crítico caído, mostrarlo inmediatamente.

Ejemplo:

🔴 INCIDENCIA CRÍTICA

TORRE PUJILÍ

Sin conexión desde: 05:42

Última comunicación: 05:41:48

Duración de caída: 3h 27m

Clientes posiblemente afectados: 37

Botón:

VER DETALLE

---

# 3. NIVELES DE ALERTA

Manejar al menos:

## 🔴 CRÍTICA

Para:

* Torre caída.
* OLT caída.
* Router principal caído.
* Radioenlace principal caído.
* Nodo importante sin comunicación.

## 🟠 ADVERTENCIA

Para:

* Alta latencia.
* Pérdida de paquetes.
* Enlace inestable.
* Parámetros fuera de rango.
* Equipo degradado.

## 🟢 RECUPERADO

Cuando un equipo vuelva a responder.

Ejemplo:

TORRE PUJILÍ

Servicio recuperado: 07:48

Tiempo total de caída: 2h 06m

---

# 8. CRUCE ENTRE INCIDENCIAS Y ÓRDENES

Esta parte es MUY IMPORTANTE.

Cuando un técnico abra una orden de un cliente, el sistema debe verificar si el cliente depende de una torre, nodo, OLT, enlace u otro equipo que actualmente tenga una incidencia.

Si existe una incidencia mostrar:

⚠️ ATENCIÓN

El cliente está conectado a:

TORRE PUJILÍ

Actualmente se encuentra OFFLINE desde las 05:42.

El inconveniente del cliente puede estar relacionado con una incidencia general de red.

Botón:

VER INCIDENCIA

Esto permitirá evitar visitas innecesarias.

El técnico podrá continuar con la orden si corresponde, pero debe recibir esta advertencia.

# SEGURIDAD DE INFRAESTRUCTURA

El navegador del técnico NO debe conectarse directamente a:

* MikroTik.
* OLT.
* Routers.
* Switches.
* Radios.
* APIs administrativas de equipos.

La comunicación debe realizarse mediante el backend actual del sistema.

El backend debe entregar únicamente la información que el técnico tenga permitido consultar.

No exponer:

* Usuarios.
* Passwords.
* Tokens.
* Communities SNMP.
* API Keys.
* Credenciales SSH.
* Credenciales MikroTik.
* Credenciales OLT.

Orden recomendado de la pantalla principal:

1. Encabezado.

4. Incidencias activas.
5. Novedades importantes.
6. Mi jornada.
7. Próxima instalación.
8. Mi ruta de hoy.

Utilizar diseño limpio, profesional y moderno.

Estados visuales:

🟢 Verde = operativo.

🟠 Amarillo/naranja = advertencia.

🔴 Rojo = crítico/caído.

No saturar la pantalla.

Priorizar información útil para un técnico que se encuentra trabajando en campo.
