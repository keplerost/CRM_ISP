01 Qué va al VPS y qué no

Antes de contratar nada: no todo lo que tenés necesita un servidor, y una de las cosas que tenés no debería compartirlo con las otras.

SistemaHoy¿Al VPS?
Sistema ISP
middleware :4000 + web		 Tu PC, con túnel Sí. Es el que más gana: deja de depender de que tu máquina esté prendida.
Base de datos
Supabase		 Nube No. Ya está afuera y administrada. Moverla a mano es cambiar un problema resuelto por uno tuyo.
CRM / bot de WhatsApp Supabase Edge Functions Solo si querés. Ya corre en la nube. Se mueve si te conviene tenerlo bajo tu control o si el proveedor lo entrega como código.
Servidor de licencias
:4100		 Sin desplegar Sí, pero APARTE. Ver abajo.
El servidor de licencias va solo

Es el lado del vendedor: es lo que habilita a cada ISP que te compró el sistema. Si vive en el mismo servidor que la instalación de un cliente, ese cliente está a un descuido de poder apagar su propio control de licencia — o de ver los datos de todos los demás ISP.

Va en un VPS propio, o al menos en uno que nunca comparta con la instalación de un cliente. Es el único de los cuatro donde la separación no es prolijidad sino modelo de negocio.

02 La restricción que decide todo

El middleware no solo habla con la base. Abre sesiones SSH contra las OLT —PROGRESO y LA MANÁ— y usa la API de RouterOS contra los MikroTik para cortar y reconectar abonados.

Esos equipos están en tu red, con direcciones privadas. Un VPS en internet no los alcanza. Si movés el middleware sin resolver esto, todo lo que es facturación y consulta va a andar, y todo lo que toca la red va a fallar: los cortes por mora, las reconexiones al cobrar, el aprovisionamiento de una ONT.

Hay dos salidas, y la elección cambia todo el resto.

A · Middleware en el VPS + VPNB · Middleware local, solo la web afuera
Cómo El VPS es concentrador VPN; cada MikroTik se conecta hacia él. El middleware se queda donde está; el VPS solo sirve la web.
Si se corta tu internet El sistema sigue: facturación, consultas, el CRM. Se cae todo.
Trabajo de montaje Más: hay que tocar cada router. Casi nada.
Ya está escrito deploy/openvpn-server.sh y agregar-cliente-vpn.sh Es lo que tenés hoy con el túnel.
La recomendación

A, y por una razón que no es técnica: un ISP que factura no puede depender de que una PC de la oficina esté prendida. La VPN es trabajo de una tarde y se hace una sola vez por router.

El camino B es legítimo como paso intermedio mientras probás, pero no como destino.

Lo que hay que decidir antes de contratar el VPS

Los MikroTik van a guardar la dirección del VPS en su configuración. Si un día cambiás de proveedor y cambia la IP, a los routers sin IP pública no los vas a poder alcanzar para corregirlos.

Por eso: en la configuración de los routers poné un dominio —vpn.smartbotai.net— y no la IP. Ya tenés el dominio en Cloudflare; el registro se cambia en un minuto y los routers siguen encontrando el servidor.

03 El mapa del servidor

Varios sistemas en una máquina funcionan si cada uno tiene lo suyo: su puerto, su usuario, su carpeta, su servicio y su subdominio. Lo único compartido es el portero.

VPS · Debian 12
nginx · :80 y :443 el único que mira a internet · reparte por subdominio
gestion.smartbotai.net → sistema ISP web estática en /opt/smartolt/web/dist
/api → 127.0.0.1:4000 · usuario smartolt
api.smartbotai.net → la misma API, para el CRM solo /api/v1 y /api/integracion · 127.0.0.1:4000
crm.smartbotai.net → bot de WhatsApp 127.0.0.1:4200 · usuario crmbot
OpenVPN · :1194/tcp 10.8.0.0/24 → un túnel por MikroTik → las OLT detrás
SistemaPuerto internoUsuarioCarpeta
Sistema ISP4000smartolt/opt/smartolt
Servidor de licencias4100licencias/opt/licencias
CRM / bot4200crmbot/opt/crm
Pruebas del ISP4900smartolt-test/opt/smartolt-test
Las dos reglas que hacen que esto funcione
  1. Nada escucha en la interfaz pública, solo en 127.0.0.1. Se llega únicamente por nginx. Un servicio con un puerto abierto a internet es un servicio que alguien va a encontrar.
  2. Un usuario del sistema por aplicación. Si mañana el CRM tiene una falla, el atacante entra como crmbot — que no puede leer el .env del sistema ISP ni tocar sus archivos. Sin esa separación, una falla en el sistema menos importante compromete al más importante.

04 Cuánto VPS hace falta

Menos del que te van a querer vender. La base de datos está afuera, que es lo que normalmente pide memoria.

EscenariovCPURAMDiscoPrecio típico
Solo el sistema ISP12 GB25 GB~USD 12
ISP + CRM + pruebas24 GB50 GB~USD 24
Licencias (aparte)11 GB10 GB~USD 6

Dos datos concretos de este proyecto para dimensionar: web/node_modules pesa 184 MB y middleware/node_modules otros 75 MB. Compilar el frontend es lo más pesado que va a hacer la máquina, y es puntual.

Dónde ponerlo

Elegí una región cercana —Miami o São Paulo para Ecuador—. No es por la web: es porque cada operación contra una OLT abre una sesión SSH y encadena comandos, y ahí la latencia se multiplica por cada ida y vuelta.

05 La base del servidor

Lo que se hace una sola vez, antes de instalar ninguna aplicación.

Entrar y cerrar la puerta

ssh root@TU-IP

adduser opero
usermod -aG sudo opero
mkdir -p /home/opero/.ssh
cp ~/.ssh/authorized_keys /home/opero/.ssh/
chown -R opero:opero /home/opero/.ssh
chmod 700 /home/opero/.ssh

Y se desactiva el ingreso con contraseña, que es por donde entran solos:

nano /etc/ssh/sshd_config
    PermitRootLogin no
    PasswordAuthentication no
systemctl restart ssh
No cierres la sesión todavía

Abrí una segunda terminal y comprobá que entrás como opero. Si algo quedó mal y ya cerraste la única sesión que tenías, la forma de recuperarlo es la consola de emergencia del proveedor — que existe, pero es una hora perdida.

El cortafuegos

apt install -y ufw
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 1194/tcp      # OpenVPN, si vas por el camino A
ufw enable

Fijate que no se abre el 4000, ni el 4100, ni el 4200. Esos solo se alcanzan desde adentro.

Lo mínimo que evita disgustos

apt install -y fail2ban unattended-upgrades
timedatectl set-timezone America/Guayaquil

La zona horaria no es un detalle cosmético: la facturación mensual, los cortes por mora y los avisos programados se disparan por hora. Con el servidor en UTC, un corte de las 8 de la mañana sale a las 3.

06 Montar el sistema ISP

Esta parte ya está escrita en deploy/. El guion completo está en deploy/README.md; acá va lo que importa entender. 

git clone TU-REPO /opt/smartolt
cd /opt/smartolt/deploy
chmod +x *.sh
./install-app.sh

Instala Node 22, nginx, crea el usuario smartolt, instala dependencias, compila el frontend y deja el middleware bajo systemd.

La línea que rompe la instalación

En web/.env, VITE_API_URL tiene que ser la URL pública: 

VITE_API_URL=https://gestion.smartbotai.net/api

Con localhost ahí, la web compila bien, carga bien, y no funciona nada — porque el navegador del usuario busca el puerto 4000 en su propia máquina. Es el mismo malentendido que hacía que el CRM no llegara a tu PC.

Y como se compila adentro del paquete, cambiarla después obliga a recompilar: no alcanza con reiniciar el servicio.

La VPN, si vas por el camino A

./openvpn-server.sh                          # una vez
./agregar-cliente-vpn.sh cliente01 10.8.0.11 # uno por MikroTik

El segundo imprime el script listo para pegar en el router. Después, en la web: MikroTik → Nuevo router, con la IP de la VPN (10.8.0.11) en vez de la privada.

Sobre estos scripts

El propio deploy/README.md avisa que no fueron probados contra un VPS real. Son cortos a propósito para poder leerlos enteros antes de correrlos. Leelos.

07 El patrón para el segundo

A partir del segundo sistema, es siempre lo mismo. Cuatro pasos, y el único que cambia es el nombre.

1 · Su propio usuario y carpeta

adduser --system --group --home /opt/crm crmbot
git clone TU-REPO-DEL-CRM /opt/crm
chown -R crmbot:crmbot /opt/crm

2 · Su propio servicio

En /etc/systemd/system/crm.service:

[Unit]
Description=CRM / bot de WhatsApp
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=crmbot
Group=crmbot
WorkingDirectory=/opt/crm
ExecStart=/usr/bin/node src/server.js
Environment=PORT=4200
Restart=always
RestartSec=5

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/crm

[Install]
WantedBy=multi-user.target

Es el mismo archivo que deploy/smartolt-middleware.service, con otro nombre y otro puerto. Las líneas de endurecimiento del final valen la pena: ProtectHome y ProtectSystem=strict son lo que hace que un sistema comprometido no vea al de al lado. 

systemctl daemon-reload
systemctl enable --now crm
systemctl status crm

3 · Su subdominio en nginx

En /etc/nginx/sites-available/crm:

server {
    listen 80;
    server_name crm.smartbotai.net;

    location / {
        proxy_pass http://127.0.0.1:4200;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
ln -s /etc/nginx/sites-available/crm /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

nginx -t antes de recargar, siempre. Recargar con un error de sintaxis tumba todos los sitios, no solo el que tocaste.

4 · El DNS y el certificado

En Cloudflare, un registro A de crm hacia la IP del VPS. Y después: 

apt install -y certbot python3-certbot-nginx
certbot --nginx -d gestion.smartbotai.net -d api.smartbotai.net -d crm.smartbotai.net
Cuidado con la nube naranja

Si el registro está proxeado (nube naranja), certbot no puede validar por HTTP: Cloudflare intercepta el pedido y el certificado falla. Ponelo en gris, sacá el certificado, y si querés volvelo a naranja después.

08 Probar sin romper lo que factura

Acá está el corazón de la pregunta, y es donde más fácil se pierde plata.

Tu sistema cobra de verdad: acredita pagos, salda facturas, corta y reconecta abonados. Una prueba contra la base de producción no es una prueba — es una operación real hecha sin querer.

Esto pasó, no es hipotético

Probando el registro de pagos por la API, dos pedidos de prueba con una llave que tenía «acreditar al instante» encendido entraron como cobros reales: USD 46,20 acreditados a un abonado, facturas saldadas incluidas. Se pudieron revertir porque se detectaron en el momento y se sabía exactamente qué filas tocar.

Un mes después, eso mismo aparece en el cierre de caja, en la comisión de un vendedor y en el reporte de ARCOTEL — y ya no se revierte, se explica.

La regla

Una sola cosa que recordar

Ambiente de prueba = base de datos distinta. Todo lo demás —otro puerto, otro usuario, otro subdominio— es comodidad. Lo que impide el desastre es que la base no sea la misma.

Cómo se arma

1 · Un proyecto Supabase aparte. Gratis. Le corrés las mismas migraciones en orden, desde la 01 hasta la última: 

npm run check:migraciones

Lee la base y dice cuál falta, columna por columna, sin modificar nada. Es la forma de saber que el ambiente de prueba es igual al de producción.

2 · Una copia del sistema apuntando ahí. Mismo código, .env distinto: 

/opt/smartolt-test           puerto 4900   usuario smartolt-test
    SUPABASE_URL=https://EL-PROYECTO-DE-PRUEBA.supabase.co
    PORT=4900

3 · Datos que se noten. Abonados llamados PRUEBA UNO, cédulas 99900030, montos con centavos raros. Cuando algo se filtre entre ambientes —y en algún momento pasa— se tiene que ver de una.

4 · Que no pueda mandar mensajes de verdad. Es lo que más se olvida. En el ambiente de prueba, la vía de WhatsApp en manual y el correo sin credenciales. Un aviso de corte de prueba enviado a 180 abonados reales cuesta el número de WhatsApp.

Qué probar, en este orden

PruebaQué confirma
1 curl .../api/integracion/ping con llave y sin llave Llega, y la seguridad está en pie
2 Entrar a la web, iniciar sesión, abrir un abonado El frontend habla con su API
3 Consultar deuda por la API La cadena completa hasta la base
4 Registrar un pago sin acreditación automática Escribe, y queda en la bandeja para confirmar
5 Diagnosticar un abonado contra una OLT Que la VPN sirve. Es la prueba que separa el camino A del B
6 Cortar y reconectar un abonado de prueba El MikroTik responde por el túnel
7 Reiniciar el VPS y no tocar nada Todo vuelve solo

Las primeras cuatro se prueban contra el ambiente de prueba. La quinta y la sexta tocan equipos reales aunque la base sea de prueba —no hay OLT de mentira— así que se hacen con un abonado tuyo, fuera de hora pico, y con alguien mirando el equipo.

La prueba que vale por todas

Reiniciar el servidor. Es la única que cubre servicios, orden de arranque, permisos, certificados y VPN de una sola vez. Hacela antes de mandar clientes ahí, no después.

09 La mudanza, en orden

Nada de esto se hace de golpe. El sistema de hoy sigue andando en tu PC hasta el último paso.

PasoSe puede volver atrás
1Contratar el VPS y dejarlo seguro (sección 5)Sí
2Montar el ambiente de prueba, con su Supabase aparteSí
3Correr las pruebas 1 a 4Sí
4Montar la VPN y sumar un MikroTikSí
5Pruebas 5 y 6 con un abonado tuyoSí
6Montar producción en el mismo VPS, apuntando al Supabase realSí, todavía nadie la usa
7Sumar el resto de los MikroTikCon cuidado
8Mover el DNS de api.smartbotai.net al VPSSí, pero es el punto de no retorno práctico
9Apagar el túnel y los servicios de la PCRecién cuando el paso 8 lleve días bien
El paso 8, en detalle

Hoy api.smartbotai.net es un CNAME al túnel de tu PC. Mudarlo es cambiarlo por un A a la IP del VPS.

Bajá el TTL a 60 segundos un día antes. Así, si algo sale mal, volver atrás tarda un minuto en vez de horas. Y no hace falta avisarle nada al proveedor del CRM: la URL no cambia, cambia a dónde apunta.

Los dos ambientes contra la misma base, nunca

Entre los pasos 6 y 9 vas a tener el sistema corriendo en dos lados. Si los dos apuntan al Supabase real, las dos instancias corren las tareas automáticas: doble facturación mensual, doble aviso de corte, dobles cobros aplicados.

Antes de levantar producción en el VPS, apagá las automatizaciones en la PC —o el servicio entero— y dejá una sola instancia con las tareas encendidas.

10 Operar y respaldar

Los comandos de todos los días

systemctl status smartolt-middleware        # ¿está vivo?
journalctl -u smartolt-middleware -f        # ver en vivo
journalctl -u smartolt-middleware -n 100    # las últimas 100 líneas
systemctl restart smartolt-middleware       # después de tocar código

systemctl status openvpn-server@server      # la VPN
cat /var/log/openvpn/status.log             # qué routers están conectados
nginx -t && systemctl reload nginx          # después de tocar nginx

Actualizar

cd /opt/smartolt
git pull
npm --prefix middleware install
npm --prefix web install && npm --prefix web run build
systemctl restart smartolt-middleware

El build del frontend no es opcional si tocaste la web: nginx sirve dist/, no el código fuente.

Qué respaldar

QuéDóndeSi se pierde
La base Supabase Lo peor que puede pasar. Activá los respaldos automáticos y bajate uno a mano cada tanto: un respaldo que nunca se restauró no es un respaldo.
Los .env /opt/*/. env Reconstruibles, pero es un día de trabajo. No van al repositorio.
Certificados de la VPN /etc/openvpn Hay que reconfigurar todos los routers. Copialos.
La clave de licencias /opt/licencias Se caen las licencias de todos tus clientes a la vez.

Los snapshots del proveedor cubren el servidor entero por unos dólares al mes y se restauran en minutos. Para lo que vale lo que hay ahí adentro, es barato.

11 Los errores caros

Probar contra la base de producción

El más caro de todos, y el más fácil de cometer porque «era solo una prueba». Un ambiente de prueba con su propia base cuesta cero.

Dos instancias con las tareas encendidas

Facturación duplicada, avisos duplicados, cortes duplicados. Y se descubre cuando llaman los abonados.

La IP del VPS en la configuración de los MikroTik

El día que cambies de servidor, a los routers sin IP pública no los vas a poder alcanzar. Usá un dominio desde el principio.

Exponer un puerto de aplicación a internet

El 4000, el 4200, o el de Supabase. Todo entra por nginx; lo demás escucha en 127.0.0.1 y nada más.

Poner el servidor de licencias con un cliente

Es el control de acceso de tu negocio. Va solo.

Y uno que no es caro pero desespera

VITE_API_URL con localhost. La web carga perfecto y no anda nada. Se arregla corrigiendo el .env y recompilando — reiniciar el servicio no alcanza, porque ese valor quedó adentro del paquete.
